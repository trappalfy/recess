# Recess — корректирующий бриф №1: вместо waitlist — рабочий продукт

Этот документ дополняет основной бриф (`recess-site-brief.md`) и **имеет приоритет** там, где они расходятся. Визуал, токены, анимации и ассеты лендинга остаются как в основном брифе.

## ⚠️ Главное ограничение этапа: никакого бэкенда

Порядок жёсткий. Сначала готовый сайт под рабочий мейннет-продукт. Потом, отдельным этапом, контракты и весь бэкенд.

На этом этапе **не создавать**:

- смарт-контракты, файлы `.sol`, Hardhat, Foundry, скрипты деплоя и тесты контрактов;
- API-роуты (`app/api/*`), server actions, которые пишут данные, и любые собственные серверные эндпоинты;
- базы данных, ORM, миграции, Supabase, Redis и подобное;
- индексаторы, сабграфы, кроны, воркеры, очереди;
- авторизацию, аккаунты, сессии на сервере;
- сервисы-прокси для RPC и цен.

Что делаем вместо этого:

- весь фронтенд полностью, как для мейннета: все экраны, состояния и тексты финальные;
- слой-адаптер из раздела 6 с `MockClient`;
- `ChainClient` только как пустую заготовку с TODO;
- `abi.ts` — только TypeScript-типы и черновик ABI, без Solidity.

Всё, чего не хватает без бэкенда, закрывается демо-данными из `MockClient` с видимой плашкой `Demo data`.

Если задача кажется невыполнимой без бэкенда — остановиться и спросить, а не строить его.

Сайт делается под мейннет: конфиг сети по умолчанию — мейннет Robinhood Chain (параметры из env). Никаких тестнет-кранов и тестнет-плашек в интерфейсе.

## 0. Что меняется

Waitlist больше не нужен. Конечный результат — лендинг плюс приложение, через которое пользователь торгует: подключает кошелёк, выбирает тикер и сторону, ставит USDG, забирает выигрыш.

Контрактов и бэкенда пока нет — они следующий этап. Поэтому приложение строим полностью, но работает оно через слой-адаптер:

- сейчас — на демо-данных (`mock`);
- потом — на контрактах (`chain`), без переделки UI.

## 3. Механика продукта (что строит UI)

### 3.1 Рынок

Один рынок = один тикер на одни выходные (эпоху). Вопрос: цена первой свежей котировки референса после выходных будет выше пятничного закрытия или ниже.

- Стороны: `Above` и `Below`.
- Ставки в USDG, пул-тотализатор: обе стороны кладут в один пул.
- Выигравшая сторона делит пул за вычетом комиссии пропорционально ставкам.
- Референс: фид Chainlink по тикеру. Цена пула на DEX — только для информации, в расчёте не участвует.

### 3.2 Расписание эпохи

Всё задаётся в конфиге `lib/recess/schedule.ts`; время хранится в America/New_York, в UI показываем ET, а локальное время — в подсказке.

| Этап | Когда (по умолчанию, согласовать) |
|---|---|
| Open | пятница 16:00 ET — рынки открыты, фиксируется пятничное закрытие |
| Locked | воскресенье 19:00 ET — ставки закрыты |
| Settled | первая свежая котировка референса после Locked |
| Void | см. 3.4 |

Праздничные дни и сдвиги — списком в том же конфиге.

### 3.3 Формулы

- Оценка множителя стороны: `(poolAbove + poolBelow) × (1 − feeBps / 10000) / poolSide`.
- Выплата: `stake × (totalPool × (1 − feeBps / 10000)) / winningSidePool`.
- До Locked множитель в UI всегда подписан как оценка (`est.`): он меняется с каждой ставкой.
- `feeBps` — из конфига, значение согласовать.

### 3.4 Крайние случаи (по умолчанию, согласовать)

- Первая котировка равна пятничному закрытию — рынок `Void`, всем возврат ставок.
- На момент Locked одна из сторон пуста — `Void`, возврат.
- Референс не обновился за N часов после Locked (N в конфиге) — `Void`, возврат.

## 4. Приложение: маршруты и экраны

Приложение живёт в том же Next.js-проекте.

| Маршрут | Экран |
|---|---|
| `/app` | Board — все рынки текущей эпохи |
| `/app/[ticker]` | Рынок одного тикера |
| `/app/portfolio` | Позиции пользователя |
| `/terms`, `/risk` | Заглушки, текст согласовать с юристом |

**Шапка приложения** (на всех `/app*`): слева локап знака (ведёт на `/`), по центру `Board` и `Portfolio`, справа кнопка `Connect wallet`, после подключения — адрес и баланс USDG. Под шапкой — плашка эпохи: `Weekend of Sep 11–14`, статус (`Open` / `Locked` / `Settled`), отсчёт до следующего этапа.

**Board (`/app`)** — таблица рынков. Колонки:

- тикер;
- Friday close;
- цена токена в пуле сейчас и отклонение от закрытия в %;
- пул Above и пул Below;
- полоса соотношения сторон;
- оценочные множители;
- твоя позиция;
- кнопка `Take a side` → страница рынка.

Сортировка по тикеру и по размеру пула. Поиск по тикеру. На мобиле таблица превращается в карточки.

**Рынок (`/app/[ticker]`).**

- Слева: ключевые цифры (Friday close, цена в пуле, отклонение, пулы, множители), полоса соотношения, таймлайн эпохи (Friday close → Locked → Settled), блок правил (источник расчёта, случаи Void) и лента последних ставок.
- Справа — панель ставки:
  - переключатель `Above` / `Below`;
  - поле суммы USDG, баланс и кнопка `Max`;
  - оценка выплаты и множителя;
  - кнопка действия (раздел 5).
- После Settled панель показывает результат и кнопку `Claim` либо `Refund` при Void.

**Portfolio (`/app/portfolio`)** — три вкладки:

- `Open` — ставки до расчёта;
- `Claimable` — выигрыши и возвраты с кнопками `Claim`;
- `History` — все прошлые позиции.

Пустые состояния ведут на Board: `No open positions. Pick a side on the board.`

## 5. Кошелёк, сеть, состояния

- Стек: `wagmi` + `viem`, модалка подключения — RainbowKit или ConnectKit.
- Параметры сети Robinhood Chain (chain id, RPC, explorer) и адрес USDG — только из env, в код не хардкодить.
- Если адреса контрактов не заданы, приложение работает в `mock`.

Кнопка действия в панели ставки проходит состояния в таком порядке:

| Состояние | Кнопка / сообщение |
|---|---|
| Кошелёк не подключён | `Connect wallet` |
| Не та сеть | `Switch network` |
| Сумма не введена | неактивна, `Enter an amount` |
| Не хватает USDG | неактивна, `Not enough USDG in your wallet` |
| Нужен approve | `Approve USDG` |
| Готово | `Stake on Above` / `Stake on Below` |
| Транзакция в пути | `Confirming…`, тост со ссылкой в explorer |
| Успех | тост `Stake placed`, позиция обновилась |
| Ошибка / отмена | тост с причиной: `Transaction rejected in wallet` / `Transaction failed. Try again.` |
| Рынок Locked | панель неактивна, `Betting is closed. Settles at the open.` |

## 6. Слой данных

```
lib/recess/
  types.ts        Market, Epoch, Position, Side, Status
  client.ts       interface RecessClient
  mock.ts         MockClient — детерминированные демо-данные, транзакции с задержкой 1.5s
  chain.ts        ChainClient — пустая реализация с TODO под контракты
  abi.ts          черновик ABI (ниже)
  schedule.ts     расписание эпох
  config.ts       feeBps, voidAfterHours, тикеры, env
```

`RecessClient`:

- `getEpoch()`
- `listMarkets(epochId)`
- `getMarket(epochId, ticker)`
- `getPositions(address)`
- `stake(marketId, side, amount)`
- `claim(marketId)`
- `approveUsdg(amount)`

UI обращается только к интерфейсу. Режим выбирается через `NEXT_PUBLIC_RECESS_MODE=mock|chain`.

В режиме `mock` в шапке приложения всегда видна плашка `Demo data`: демо-цифры не должны выглядеть как реальные.

Черновик интерфейса контракта — чтобы следующий этап совпал с UI. Может меняться, правки должны оставаться внутри `chain.ts` и `abi.ts`:

```solidity
interface IRecessMarkets {
    enum Side { Above, Below }
    enum Status { Open, Locked, Settled, Void }

    function stake(bytes32 marketId, Side side, uint256 amount) external;
    function claim(bytes32 marketId) external returns (uint256 paid);

    function market(bytes32 marketId) external view returns (
        bytes32 ticker, uint64 openTime, uint64 lockTime,
        int256 fridayClose, int256 settlePrice,
        uint256 poolAbove, uint256 poolBelow, Status status, Side winner
    );
    function positionOf(bytes32 marketId, address user)
        external view returns (uint256 above, uint256 below, bool claimed);

    event Staked(bytes32 indexed marketId, address indexed user, Side side, uint256 amount);
    event Settled(bytes32 indexed marketId, int256 settlePrice, Side winner);
    event Voided(bytes32 indexed marketId);
    event Claimed(bytes32 indexed marketId, address indexed user, uint256 amount);
}
```

Ленту ставок и историю сейчас отдаёт `MockClient`. На этапе бэкенда их будет отдавать индексатор событий — в интерфейсе для этого предусмотреть `listActivity(marketId)`.

## 7. Дизайн приложения

Тот же язык, что у лендинга, без героя и 3D-объектов:

- белый фон, карточки с радиусом 32 и бордером `line`;
- заголовки Jakarta 500, текст Inter;
- цифры — Inter с `font-variant-numeric: tabular-nums`;
- основная кнопка — тёмная пилюля `ink`, активная сторона — `blue`;
- цвета сторон: Above — `teal-bottom` (#0EE8CC), Below — сиреневый #A48CFE, как у плиток на лендинге;
- тосты и модалки — тот же радиус и бордер.

Анимации в приложении — только отклик на действия (переключение стороны, обновление полосы, тосты). Никаких появлений по скроллу.

- Страницы `/terms` и `/risk` — заглушки с пометкой, что текст готовит юрист.

## 9. Порядок работ и приёмка

1. Правки лендинга из раздела 2.
2. Слой данных и `MockClient`.
3. Шапка, Board, страница рынка, Portfolio.
4. Кошелёк и все состояния из раздела 5.
5. Модалка и заглушки из раздела 8.

Готово, когда:

- в режиме `mock` можно подключить кошелёк, поставить на обе стороны, дождаться смоделированного расчёта (в `mock` есть кнопка разработчика «перемотать эпоху») и забрать выигрыш или возврат;
- все состояния из раздела 5 воспроизводятся;
- на лендинге не осталось ни одного упоминания waitlist;
- в репозитории нет ни контрактов, ни `app/api`, ни базы, ни серверного кода, который хранит данные: проект собирается и работает как чистый фронтенд.
